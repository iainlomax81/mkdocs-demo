2.1 Business Domain Model

Document Version: 1.0
Date: 2026-06-09
Status: Current State Analysis

Executive Summary

The Agathas Storefront is an e-commerce platform operating in the retail domain, specifically focused on online product sales with shopping cart, checkout, and order management capabilities. The system implements a rich domain model following Domain-Driven Design (DDD) principles with well-encapsulated business rules and clear aggregate boundaries.

Key Domain Characteristics: - Domain Type: E-commerce / Online Retail - Primary Business Functions: Product catalog browsing, shopping cart management, checkout processing, customer account management, and order fulfillment - Domain Model Maturity: High - implements DDD patterns with aggregate roots, value objects, domain events, and encapsulated business rules - Business Rule Encapsulation: Excellent - business rules are encapsulated within domain entities using dedicated business rule classes

Domain Model Highlights: - 4 core aggregates (Product, Basket, Order, Customer) with well-defined boundaries - Rich domain entities with encapsulated business logic - Business rules enforced through dedicated rule classes (e.g., BasketBusinessRules, OrderBusinessRules) - Domain events for cross-aggregate coordination - Value objects for address, payment, and shipping concepts

1. Business Domain Overview

1.1 Domain Description

The Agathas Storefront operates in the e-commerce retail domain, providing a complete online shopping experience from product discovery through order fulfillment. The business domain encompasses:

Core Business Areas: 1. Product Catalog Management - Managing product hierarchies, categories, brands, sizes, and colors 2. Shopping Experience - Enabling customers to browse, search, filter, and add products to shopping basket 3. Customer Management - Managing customer accounts, profiles, delivery addresses, and authentication 4. Order Processing - Handling checkout, payment processing, order submission, and order history 5. Payment Integration - Integrating with external payment provider (PayPal) for secure payment processing 6. Shipping Management - Managing delivery options, shipping services, and courier information

Business Model: - B2C (Business-to-Consumer) e-commerce platform - Product-based sales (physical goods with size/color variations) - Single-currency operation (determined by payment provider configuration) - Third-party payment processing (PayPal) - Customer account-based purchasing (registration required for checkout)

1.2 Domain Boundaries

The domain is bounded by the following context boundaries:

Within Domain (Internal): - Product catalog and categorization - Shopping basket state management - Customer account and profile management - Order lifecycle management - Business rule validation and enforcement - Domain event coordination

Outside Domain (External Integrations): - Payment processing (delegated to PayPal) - Social authentication (delegated to Janrain) - Email notifications (delegated to SMTP service) - Product content management (assumed external)

2.2 Product Aggregate

Aggregate Root: ProductTitle (located in Agathas.Storefront.Model.Products)

Purpose: Represents the product catalog with master products and their variants (size/color combinations).

Business Concept: In retail, a "product" (e.g., "Designer Dress") comes in multiple variants (Small/Red, Medium/Blue, etc.). The ProductTitle represents the master product, while Product represents individual variants that can be purchased.

Entities within Aggregate:

Entity Type Description Key Properties Business Rules
ProductTitle Aggregate Root Master product definition Name, Description, Price, ImageUrl, Brand, Category Price is defined at ProductTitle level
Product Entity Specific product variant Size, Color, ProductTitle reference Must reference a valid ProductTitle
ProductSize Value Object Size attribute (S, M, L, XL, etc.) Name Predefined set of sizes
ProductColor Value Object Color attribute Name Predefined set of colors
Brand Entity Product brand/manufacturer Name Referenced by ProductTitle
Category Entity Product categorization Name, ParentCategory Hierarchical structure

Key Business Rules (from AddressBusinessRules.cs and domain classes): - Product variants inherit price from ProductTitle - Each Product must have exactly one size and one color - Product references are immutable after creation - Category hierarchy allows nested categorization

Relationships: - One ProductTitle → Many Products (variants) - One Brand → Many ProductTitles - One Category → Many ProductTitles - Product → One ProductTitle (immutable reference)

2.3 Basket Aggregate

Aggregate Root: Basket (located in Agathas.Storefront.Model/Basket/Basket.cs)

Purpose: Manages the customer's shopping cart, including items, quantities, and delivery options.

Business Concept: A shopping basket that temporarily holds products the customer intends to purchase. The basket calculates totals including delivery costs and enforces business rules about item quantities and delivery requirements.

Entities within Aggregate:

Entity Type Description Key Properties Business Rules
Basket Aggregate Root Shopping cart Items (collection), DeliveryOption, BasketTotal, ItemsTotal Must have delivery option before checkout
BasketItem Entity Line item in basket Product (reference), Quantity, Basket (parent) Quantity must be > 0
DeliveryOption Entity Selected delivery method Cost, Name Required before proceeding to checkout

Key Business Rules (from business-rules.json): 1. No Duplicate Products: Cannot add same product twice; instead increases quantity of existing item 2. Quantity Validation: Each basket item must have quantity > 0 3. Total Calculation: Basket total = sum of (item price × quantity) + delivery cost 4. Delivery Requirement: Delivery option must be selected before checkout 5. Item Addition: Adding product creates new BasketItem or increments existing item quantity

Implementation Location: - Business rules enforced in Basket.Add() method (lines 38-41) - Quantity validation in BasketItem.IncreaseItemQtyBy() and BasketItem.DecreaseItemQtyBy() - Total calculation in Basket.BasketTotal property (line 26)

Purpose: Represents a customer's purchase order with payment and fulfillment information.

Business Concept: An immutable record of a customer's purchase, including items ordered, payment received, shipping details, and order status. Orders follow a state machine pattern for lifecycle management.

Key Business Rules (from business-rules.json): 1. Minimum Items: Order must have at least one order item 2. Payment Matching: Payment amount must exactly match order total 3. Immutability After Payment: Cannot modify order after payment received 4. No Duplicate Payment: Cannot pay for already-paid order 5. State Progression: Order state transitions follow strict sequence (Open → PaymentReceived → Submitted) 6. 2.5 Customer Aggregate

Aggregate Root: Customer (located in Agathas.Storefront.Model.Customers)

Purpose: Represents a registered customer with account details and delivery addresses.

Business Concept: A customer account that maintains authentication credentials, profile information, and saved delivery addresses for streamlined checkout.

Entities within Aggregate:

Entity Type Description Key Properties Business Rules
Customer Aggregate Root Customer account EmailAddress, FirstName, Surname, DeliveryAddresses Email must be unique and valid
DeliveryAddress Entity Saved shipping address StreetAddress, City, Postcode, FirstName, Surname Must pass address validation

Key Business Rules (from AddressBusinessRules.cs and business-rules.json): 1. Unique Email: Customer email address must be unique across all customers 2. Email Validation: Email must be in valid format (enforced by EmailValidationSpecification) 3. Checkout Address Requirement: Customer must have at least one delivery address before completing checkout 4. Address Validation: All address fields must be populated and valid

Implementation Location: - Email validation in EmailValidationSpecification class - Address business rules in AddressBusinessRules.cs - Customer business rules in CustomerBusinessRules class

2.7 Aggregate Boundaries and Consistency

Design Principles: 1. Transaction Boundaries: Each aggregate is a transaction boundary - changes within an aggregate are atomic 2. Identity References: Aggregates reference each other by ID, not by object reference 3. Consistency Enforcement: Business rules are enforced within aggregate boundaries 4. Aggregate Independence: Each aggregate can be modified independently

Consistency Rules:

Aggregate Consistency Scope Transaction Boundary
Product Product catalog integrity ProductTitle + variants
Basket Cart totals and delivery Basket + items
Order Order totals and payment Order + items + payment
Customer Customer profile and addresses Customer + addresses

Cross-Aggregate Operations: - Basket → Product: Reference by ID (eventual consistency acceptable) - Order → Customer: Reference by ID (eventual consistency acceptable) - OrderItem → Product: Snapshot product details (no reference after creation)

4. Business Rules Catalog

The system implements comprehensive business rules encapsulated within domain entities and dedicated business rule classes. Business rules are enforced at the domain layer, ensuring data integrity and business logic consistency.

4.1 Business Rule Organization

Architecture Pattern: Dedicated business rule classes that encapsulate validation and business logic separate from domain entities.

Implementation Approach: - BusinessRule<T> base class provides validation framework - Dedicated rule classes per aggregate: BasketBusinessRules, OrderBusinessRules, CustomerBusinessRules, AddressBusinessRules - Specification pattern for complex validations: EmailValidationSpecification - Rules invoked from domain entity methods before state changes

Rule Enforcement Locations: 1. Domain Entities: Rules embedded in entity methods (e.g., Basket.Add(), Order.SetPayment()) 2. Business Rule Classes: Dedicated classes in Agathas.Storefront.Model namespace 3. Validation Specifications: Specification pattern classes for reusable validations 4. Service Layer: Workflow-level validations in service implementations

5. Domain Events

The system implements a Domain Events pattern for cross-aggregate coordination and side effects, enabling loose coupling between domain concerns.

5.1 Domain Events Overview

Pattern Implementation: In-process synchronous domain events using static dispatcher

Purpose: Decouple order submission from email notification, allowing the order aggregate to remain focused on order management while external concerns (email) are handled by separate handlers.

Architecture:

graph LR A[Order.Submit] --> B[Raise OrderSubmittedEvent] B --> C[DomainEvents Dispatcher] C --> D[OrderSubmittedHandler] D --> E[IEmailService] E --> F[Send Confirmation Email]
Hold "Alt" / "Option" to enable pan & zoom

Key Characteristics: - Execution Model: Synchronous in-process (not message queue) - Transaction Scope: Handlers execute within the same transaction as the domain operation - Registration: Handlers registered via StructureMap IoC container - Dispatch: Static DomainEvents.Raise<T>() method

5.2 Implemented Domain Events

OrderSubmittedEvent

Location: Agathas.Storefront.Model.Orders.Events.OrderSubmittedEvent

Purpose: Notifies the system that an order has been successfully submitted and paid.

Trigger: When order transitions to Submitted state via Order.State.Submit()

Event Data: - Complete Order aggregate (Order entity with items, payment, shipping) - Customer information - Order timestamp - Payment confirmation

Handlers:

Handler Action Purpose Transaction
OrderSubmittedHandler Sends order confirmation email Customer notification Same transaction

Handler Implementation: 

// From OrderSubmittedHandler.cs (in Agathas.Storefront.Services.DomainEventHandlers)
public class OrderSubmittedHandler : IDomainEventHandler<OrderSubmittedEvent>
{
    private readonly IEmailService _emailService;

    public void Handle(OrderSubmittedEvent args)
    {
        _emailService.SendOrderConfirmation(args.Order);
    }
}

Event Raising Location: 

// From Order.cs - Submitted state
public void Submit()
{
    _order.State = OrderStates.Submitted;
    DomainEvents.Raise(new OrderSubmittedEvent(_order)); // Event raised here
}

Business Impact: - Ensures customers receive order confirmation immediately after payment - Decouples order domain logic from email infrastructure - Allows additional handlers to be added without modifying Order entity

5.3 Domain Event Infrastructure

Dispatcher: DomainEvents static class (in Agathas.Storefront.Infrastructure.Domain)

Handler Interface: 

public interface IDomainEventHandler<T> where T : IDomainEvent
{
    void Handle(T args);
}

Handler Factory: IDomainEventHandlerFactory resolves handlers from IoC container (StructureMap)

Registration: 

// From StructureMap registry
For<IDomainEventHandler<OrderSubmittedEvent>>()
    .Use<OrderSubmittedHandler>();

Execution Flow: 1. Domain entity raises event: DomainEvents.Raise(new OrderSubmittedEvent(order)) 2. Dispatcher resolves handlers from factory: _factory.GetHandlersFor<OrderSubmittedEvent>() 3. Each handler executed synchronously: handler.Handle(eventArgs) 4. Execution within same transaction as domain operation 5. Transaction commits only if all handlers succeed

5.4 Domain Events Usage Pattern

When to Use Domain Events: ✅ Use for: - Cross-aggregate coordination (e.g., Order → Email notification) - Side effects that should happen "when X happens" (e.g., "when order submitted, send email") - Decoupling domain logic from infrastructure concerns - Audit logging and event sourcing (future) - Workflow orchestration across aggregates

❌ Don't Use for: - Intra-aggregate operations (use direct method calls) - External API calls that could fail independently (use message queue instead) - Long-running operations (current synchronous implementation blocks transaction)

Domain events play a critical role in the order submission workflow:

5.7 Domain Events Maturity Assessment

Current Maturity Level: 🟡 Basic Implementation

Strengths: - ✅ Clean pattern implementation with dispatcher and handlers - ✅ Proper separation of concerns (Order doesn't know about Email) - ✅ Extensible design (easy to add new handlers) - ✅ IoC container integration for handler resolution

Limitations: - ⚠️ Only one event implemented (underutilized pattern) - ⚠️ Synchronous execution (blocks transaction, could cause issues with slow external services) - ⚠️ No event persistence (events lost if system crashes) - ⚠️ No retry mechanism if handler fails - ⚠️ Email failure causes order submission to fail (tight coupling despite event pattern)

Modernization Opportunities: - Implement asynchronous event handling with message queue (e.g., Azure Service Bus, RabbitMQ) - Add event sourcing for audit trail and replay capability - Implement eventual consistency for non-critical handlers - Add retry and dead-letter queue for failed events - Persist events for analysis and debugging

6.1 System-Wide Invariants

These are fundamental truths that must always hold across the system:

Invariant Description Enforcement Criticality

6.2 Aggregate-Specific Invariants

Basket Aggregate: - Basket contains zero or more items (empty basket is valid) - Each basket item references a valid product - Delivery option is optional until checkout - Basket totals are derived, never stored

Order Aggregate: - Order must have at least one order item - Order items are immutable after order creation - Payment is optional until submission (null for unpaid orders) - Order state is always valid (Open, PaymentReceived, or Submitted) - Created timestamp is immutable

Customer Aggregate: - Customer must have valid email address - Customer can have zero or more delivery addresses - Delivery addresses belong to exactly one customer

Product Aggregate: - ProductTitle must have a price > 0 - Product must reference a valid ProductTitle - Product must have size and color

8.2 Saga Pattern (Checkout Process)

Pattern: Long-running business transaction spanning multiple aggregates

Implementation: Orchestrated by OrderService and CheckoutController

Steps: 1. Validate Basket - Ensure basket has items and delivery option 2. Authenticate Customer - Verify user logged in 3. Create Order - Convert basket to order aggregate 4. Process Payment - Redirect to PayPal, await callback 5. Submit Order - Update order state, trigger domain event 6. Send Confirmation - Email sent via event handler

Compensation Logic: - Payment failure → Return to basket (order not saved) - Payment cancelled → Return to basket - Email failure → Order still submitted (email is best-effort)

Transaction Boundaries: - Basket validation: Read-only - Order creation: Transaction - Payment processing: External (PayPal transaction) - Order submission + email: Single transaction (synchronous domain event)

Business Purpose: Different delivery methods (Standard, Express, Next-Day) with varying costs
