Data Architecture - Agathas.Storefront

This document provides comprehensive documentation of all data storage systems, database schemas, data flow patterns, access methods, and security considerations within the system.

Overview

The Agathas.Storefront application utilizes a dual-database architecture with SQL Server Express LocalDB instances for both application data and ASP.NET Membership authentication. Data access is implemented through NHibernate 2.1 ORM with HBM.XML mapping files, following Repository and Unit of Work patterns for clean separation between domain and data layers.

The data architecture demonstrates strong Domain-Driven Design principles with well-defined aggregates (Basket, Order, Customer, Product) and proper enforcement of aggregate boundaries. All data access flows through repository abstractions, with NHibernate providing automatic change tracking and lazy loading capabilities. Transactions are explicitly managed through the Unit of Work pattern, scoped to HTTP request boundaries for web operations.

Despite the solid architectural patterns, the implementation relies on SQL Server User Instance mode with file-based databases (AttachDbFilename), which is deprecated and unsuitable for production. The database schema is inferred from HBM.XML mappings rather than explicit DDL scripts, making schema versioning and deployment challenging.

Data Architecture Summary: - Primary Database: SQL Server Express LocalDB (User Instance mode) - Application data - Secondary Database: SQL Server Express LocalDB - ASP.NET Membership (authentication) - Data Access: NHibernate 2.1 ORM with HBM.XML mappings - Data Volume: Unknown (cannot determine from static analysis; requires production metrics) - Transaction Volume: Unknown (requires production monitoring data)

Understanding the Entity Relationship Diagram

Key Entity Groups:

  1. Product Catalog Aggregate
  2. ProductTitle: Master product record (e.g., "Nike Air Max Running Shoe")
  3. Product: Specific variant with size/color (e.g., "Nike Air Max, Size 10, Blue")
  4. Brand: Product manufacturer/brand
  5. Category: Product categorization (hierarchical with ParentCategoryId)
  6. ProductSize: Reference data for sizes (S, M, L, 10, 11, etc.)

  7. ProductColor: Reference data for colors

  8. Basket Aggregate

  9. Basket: Shopping cart for customer session/account

  10. BasketItem: Individual products in basket with quantity and price snapshot

  11. Order Aggregate

  12. Order: Submitted order (aggregate root)
  13. OrderItem: Products in order (converted from BasketItem on submission)

  14. Payment: Payment details for order (one-to-one relationship)

  15. Customer Aggregate

  16. Customer: Customer account information

  17. DeliveryAddress: Multiple shipping addresses per customer

  18. Shipping Reference Data

  19. DeliveryOption: Available shipping methods with cost and estimated days
  20. ShippingService: Shipping service details
  21. Courier: Courier company providing shipping

Key Relationships Explained:

  1. Product Variants 

    ProductTitle (1) → Product (Many)
Cardinality: One-to-many
Description: A single product title (e.g., "Nike Air Max") has multiple variant products 
differentiated by size and color combinations.

  2. Basket to Order Conversion 

    BasketItem → OrderItem (data copy on order submission)
Description: When customer submits order, basket items are copied to order items, 
freezing product name and price at time of purchase.

  3. Customer Addresses 

    Customer (1) → DeliveryAddress (Many)
Cardinality: One-to-many
Description: Customers can have multiple saved shipping addresses with one marked as default.

  4. Order Payment 

    Order (1) → Payment (1)
Cardinality: One-to-one
Description: Each order has exactly one payment record (no split payments supported).

Critical Design Patterns:

  • Soft Delete: IsActive boolean columns on Product and Customer for logical deletion
  • Price Snapshotting: OrderItem stores UnitPrice and ProductName at time of purchase (not foreign key to Product)
  • Aggregate Roots: Basket, Order, Customer, ProductTitle are aggregate roots with cascading operations
  • Audit Trail: CreatedDate, LastUpdated, OrderDate, SubmittedDate for temporal tracking
  • Hierarchical Categories: Category table has self-referencing ParentCategoryId for tree structure

Data Flow Characteristics:

  • Synchronous Processing: All operations block HTTP request thread
  • Transaction Boundaries: Unit of Work per HTTP request, explicit commit
  • Domain Events: In-process only (email sent synchronously within transaction)
  • No Async: No background jobs, queues, or eventual consistency patterns
  • Lazy Loading: Related entities loaded on-demand (N+1 query risk)

Session Management:

// NHibernate session factory (singleton)
public class NHibernateSessionFactory
{
    private static ISessionFactory _sessionFactory;

    public static ISessionFactory GetSessionFactory()
    {
        if (_sessionFactory == null)
        {
            var configuration = new Configuration();
            configuration.Configure(); // Read from hibernate.cfg.xml
            configuration.AddAssembly("Agathas.Storefront.Repository.NHibernate");
            _sessionFactory = configuration.BuildSessionFactory();
        }
        return _sessionFactory;
    }
}

// Unit of Work manages session per HTTP request
public class NHUnitOfWork : IUnitOfWork
{
    private readonly ISession _session;

    public NHUnitOfWork(ISessionFactory sessionFactory)
    {
        _session = sessionFactory.OpenSession();
    }

    public ISession GetSession() => _session;

    public void Commit()
    {
        using (var transaction = _session.BeginTransaction())
        {
            _session.Flush(); // Write pending changes
            transaction.Commit();
        }
    }

    public void Dispose()
    {
        _session?.Dispose();
    }
}

Session Storage: HTTP Context (one session per web request)

Repository Pattern Implementation

Pattern: Generic Repository with specialized interfaces

Base Repository: 

public class Repository<T> : IRepository<T> where T : class
{
    protected ISession Session { get; private set; }

    public Repository(IUnitOfWork unitOfWork)
    {
        Session = unitOfWork.GetSession();
    }

    public T FindBy(IQuery query)
    {
        var criteria = query.BuildCriteria(Session);
        return criteria.UniqueResult<T>();
    }

    public IEnumerable<T> FindAll(IQuery query)
    {
        var criteria = query.BuildCriteria(Session);
        return criteria.List<T>();
    }

    public void Save(T entity)
    {
        Session.SaveOrUpdate(entity);
    }

    public void Delete(T entity)
    {
        Session.Delete(entity);
    }
}

Specialized Repository Example: 

public class BasketRepository : Repository<Basket>, IBasketRepository
{
    public BasketRepository(IUnitOfWork unitOfWork) : base(unitOfWork) { }

    public Basket FindByCustomerId(int customerId)
    {
        return Session.Query<Basket>()
            .Where(b => b.Customer.Id == customerId)
            .Fetch(b => b.Items) // Eager load basket items
            .SingleOrDefault();
    }
}

Query Object Pattern

Purpose: Abstract query construction from repository

Example: 

public class ProductsByCategoryQuery : IQuery
{
    private readonly int _categoryId;

    public ProductsByCategoryQuery(int categoryId)
    {
        _categoryId = categoryId;
    }

    public ICriteria BuildCriteria(ISession session)
    {
        return session.CreateCriteria<Product>()
            .CreateAlias("ProductTitle", "pt")
            .Add(Restrictions.Eq("pt.Category.Id", _categoryId))
            .Add(Restrictions.Eq("IsActive", true))
            .SetMaxResults(50);
    }
}

// Usage in repository
var query = new ProductsByCategoryQuery(categoryId);
var products = repository.FindAll(query);

Lazy Loading and N+1 Problem

Lazy Loading Configuration: Enabled via LinFu proxies

N+1 Problem Risk: 

// BAD: N+1 queries
var baskets = basketRepository.FindAll();
foreach (var basket in baskets) // 1 query
{
    Console.WriteLine(basket.Items.Count); // N queries (one per basket)
}

// GOOD: Eager loading
var baskets = session.Query<Basket>()
    .Fetch(b => b.Items) // Single JOIN query
    .ToList();

Eager Loading Strategies: - Fetch in Query Objects for known access patterns - Join Fetch in HBM.XML for required associations - Batch fetching with batch-size attribute

Data Security and Compliance

Authentication Data Storage

ASP.NET Membership Provider: aspnetdb.mdf

Key Tables: - aspnet_Users - User IDs and application membership - aspnet_Membership - Passwords (hashed), email, security Q&A - aspnet_Profile - User profile data (key-value pairs)

Password Storage: - Hash Algorithm: SHA1 (default for ASP.NET Membership in .NET 3.5/4.0) - Salting: Yes (automatic per-user salt) - Iteration: Single hash iteration (weak by modern standards) - Security Assessment: ⚠️ SHA1 considered cryptographically broken; vulnerable to collision attacks

Recommendation: Migrate to ASP.NET Core Identity with PBKDF2, bcrypt, or Argon2 hashing

Encryption at Rest: - ❌ Database: SQL Server Express does not support Transparent Data Encryption (TDE) - feature only in Enterprise Edition - ❌ File System: No BitLocker or file-level encryption detected - ❌ Backups: No encrypted backups

Encryption in Transit: - ⚠️ HTTPS: Dependent on IIS configuration (not enforced in application code) - ❌ No HSTS: HTTP Strict Transport Security not configured - ❌ No Certificate Pinning: Not applicable for web applications

Recommended Encryption Strategy:

  1. Immediate:
  2. Encrypt Web.config sections: aspnet_regiis -pe "connectionStrings" -app "/AgathsStorefront"

  3. Enforce HTTPS via [RequireHttps] attribute on all controllers

  4. Short-term:

  5. Migrate secrets to Azure Key Vault or AWS Secrets Manager

  6. Implement column-level encryption for sensitive fields (use Always Encrypted if migrating to Azure SQL)

  7. Long-term:

  8. Full database encryption (TDE if using SQL Server Enterprise or Azure SQL)
  9. Implement encryption key rotation
  10. Audit logging for data access

SQL Injection Prevention

Protection Mechanism: NHibernate parameterized queries

Risk Assessment: ✅ Low

All database access flows through NHibernate ORM, which uses parameterized queries by default:

// Safe: NHibernate parameterizes automatically
var product = session.Get<Product>(productId);

// Safe: Criteria API uses parameters
var criteria = session.CreateCriteria<Product>()
    .Add(Restrictions.Eq("Id", productId)); // Parameter binding

// Safe: Query object pattern abstracts criteria
var query = new ProductsByCategoryQuery(categoryId);
var products = repository.FindAll(query);

Risk Areas: - ⚠️ No evidence of raw SQL or HQL queries with string concatenation - ✅ All queries go through Repository abstraction - ✅ No stored procedures with dynamic SQL

Performance Considerations

Query Performance

Identified Performance Risks:

  1. N+1 Query Problem:
  2. Risk: Lazy loading can trigger multiple queries
  3. Example: Loading baskets, then accessing basket.Items in loop (1 + N queries)

  4. Mitigation: Use Fetch() or eager loading in HBM.XML for known access patterns

  5. No Second-Level Caching:

  6. Impact: Every product catalog request hits database

  7. Mitigation: Enable NHibernate second-level cache (SysCache2 provider for ASP.NET cache or migrate to Redis)

  8. No Query Result Caching:

  9. Impact: Repeated identical queries (e.g., "get featured products") execute each time

  10. Mitigation: Enable NHibernate query cache

  11. Batch Size Not Optimized:

  12. Current: Batch size = 10
  13. Recommendation: Increase to 25-50 for bulk INSERT/UPDATE operations

Immediate (Switch to SQL Server Express Standard Instance):

-- Full backup (daily at 2 AM)
BACKUP DATABASE AgathesShop
TO DISK = 'C:\SQLBackups\AgathesShop_Full.bak'
WITH INIT, FORMAT, COMPRESSION;

-- Transaction log backup (every 15 minutes)
BACKUP LOG AgathesShop
TO DISK = 'C:\SQLBackups\AgathesShop_Log.trn'
WITH INIT, FORMAT, COMPRESSION;
