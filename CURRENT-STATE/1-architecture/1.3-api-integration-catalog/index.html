API Integration Catalog - Agathas.Storefront

This document provides a comprehensive catalog of all HTTP endpoints (MVC actions), external integration points, and integration patterns used within the system.

IMPORTANT NOTE: Agathas.Storefront is an ASP.NET MVC 2 server-side web application, NOT a REST API. This document catalogs MVC controller endpoints (for web page requests) and external service integrations. The application does not expose a standalone REST API for external consumers.

Executive Summary

Overview

Agathas.Storefront implements a traditional server-side MVC architecture with 9 controllers and approximately 30 HTTP endpoints serving HTML pages to web browsers. The application integrates with 3 external services (PayPal for payments, Janrain for social authentication, SMTP for email) but does not expose a REST API for third-party consumption.

All HTTP endpoints follow ASP.NET MVC 2 conventions with server-side rendering using ASPX views. A small number of endpoints return JSON for AJAX operations (product search, basket quantity updates). Authentication uses Forms Authentication with session cookies.

The architecture is monolithic with no API gateway, no rate limiting, and no API versioning. External integrations use simple protocols (HTTP POST redirects for PayPal, OAuth callbacks for Janrain, SMTP for email).

Technology Summary

HTTP Technologies: - MVC Framework: ASP.NET MVC 2 (server-side rendering) - Internal Endpoints: HTTP GET/POST to MVC controllers - AJAX Endpoints: JSON responses for specific operations (product search, basket updates) - External Protocols: HTTPS Form POST (PayPal), OAuth callback (Janrain), SMTP - Authentication: ASP.NET Forms Authentication (cookie-based) - API Gateway: None - Documentation: None (no Swagger/OpenAPI)

MVC Endpoint Catalog

Overview

The application exposes HTTP endpoints through 9 ASP.NET MVC controllers. Most endpoints return HTML views (ASPX templates) for browser rendering. A few endpoints return JSON for AJAX requests.

Endpoint Structure: 

https://[domain]/[Controller]/[Action]?[parameters]

Examples:
https://agathas-storefront.com/Product/GetProductsByCategory?categoryId=5
https://agathas-storefront.com/Basket/Add?productId=123
https://agathas-storefront.com/Order/Detail/456

Routing Convention: Default ASP.NET MVC routing (controller/action/id)

No API Versioning: All endpoints are unversioned (no v1, v2 prefixes)

1. PayPal Standard Payments

Provider: PayPal Inc.

Purpose: Credit card payment processing for customer orders

Integration Type: Redirect-based payment (PayPal Standard Payments)

Protocol: HTTPS Form POST

Direction: Bidirectional (redirect to PayPal, callback from PayPal)

Frequency: Per order submission (on-demand)

Integration Flow:

(order details, amounts, return URL) activate PayPal PayPal->>Customer: Display payment page Customer->>PayPal: Enter payment details PayPal->>PayPal: Process payment PayPal->>App: Redirect to /Payment/Complete?orderId=X&tx=ABC123 deactivate PayPal App->>App: Update Order.Payment with transaction ID App->>Customer: Display order confirmation
Hold "Alt" / "Option" to enable pan & zoom

Endpoints:

Operation Endpoint Method Purpose
Process Payment https://www.sandbox.paypal.com/cgi-bin/webscr POST Redirect customer to PayPal for payment
Payment Callback https://[app-domain]/Payment/Complete GET Receive payment completion notification

Authentication: - Method: Business email configuration (no API key for Standard Payments) - Credentials Storage: Web.config <appSettings> PLAINTEXT (security issue) - Configuration: - PayPalBusinessEmail: Merchant's PayPal account email - PayPalReturnUrl: Success callback URL - PayPalCancelUrl: Cancellation callback URL

Data Format: - Request: HTML form fields (application/x-www-form-urlencoded) - cmd=_xclick (single payment) - business=[merchant email] - item_name=[order description] - amount=[order total] - currency_code=USD - return=[success URL] - cancel_return=[cancel URL]

  • Response: Query parameters on redirect
  • tx=[transaction ID]
  • st=[status: Completed/Pending/Failed]
  • amt=[amount]
  • cc=[currency code]

Error Handling: - Retry Strategy: None (user-initiated retry) - Timeout: Dependent on customer action (no server-side timeout) - Circuit Breaker: Not applicable (redirect-based) - Fallback Strategy: Display error message, customer can retry checkout

SLA/Uptime: - Provider SLA: 99.9% (PayPal published SLA) - Expected Availability: Very high (critical payment infrastructure) - Support Contact: PayPal Merchant Technical Support

Cost Structure: - Model: Per-transaction fee - Rate: Typically 2.9% + $0.30 per transaction (merchant account specific) - Monthly Budget: Variable based on sales volume

Monitoring: - ❌ No health check endpoint - ❌ No alerting on failures - ❌ No payment success rate monitoring - Recommendation: Implement PayPal IPN (Instant Payment Notification) for reliable payment confirmation

Limitations: - Customer redirected away from site (UX disruption) - No control over payment UI - Callback reliability depends on customer completing redirect - Basic integration (no signature verification) - Sandbox mode configured (not production-ready)

Documentation: - Location: Agathas.Storefront.Infrastructure/Payments/PaypalPaymentService.cs - PayPal Docs: https://developer.paypal.com/docs/classic/paypal-payments-standard/integration-guide/

Performance Characteristics

Response Time Analysis

Cannot be measured from static analysis - requires production monitoring

Estimated Performance (based on architecture):

Endpoint Type Estimated Response Time Factors
Simple GET (cached) < 100ms If caching enabled
Product listing (no cache) 200-500ms Database query + rendering
Product detail page 100-300ms Single database lookup + related data
Add to basket 100-200ms Database write + transaction
Checkout/Order submission 500-1000ms Multiple database writes, email sending
AJAX product search 300-600ms Complex query with joins

Performance Bottlenecks:

  1. No Caching:
  2. Every product catalog request hits database

  3. Recommendation: Enable NHibernate second-level cache or output caching

  4. N+1 Query Problem:

  5. Lazy loading can trigger multiple queries

  6. Recommendation: Use eager loading (.Fetch()) for known access patterns

  7. Synchronous Email Sending:

  8. Order submission blocks until email sent (adds 100-500ms)

  9. Recommendation: Queue emails for background processing

  10. Database User Instance:

  11. Poor performance under load
  12. Recommendation: Migrate to standard SQL Server instance

Throughput

Unknown - requires load testing

Estimated Capacity: - Single server: 10-50 concurrent users (monolithic architecture, no caching) - With SQL Server standard instance: 100-200 concurrent users - With caching and optimization: 500-1000 concurrent users

Scalability Limitations: - HttpContext-scoped Unit of Work prevents horizontal scaling - No distributed caching - User Instance database cannot scale
