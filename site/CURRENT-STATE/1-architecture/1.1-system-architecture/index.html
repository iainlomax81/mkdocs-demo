Executive Summary

Agathas.Storefront is a classic ASP.NET MVC 2 e-commerce web application built on .NET Framework 3.5/4.0, representing a well-architected monolithic system following Domain-Driven Design principles and layered architecture patterns. The system was designed and implemented circa 2010, demonstrating mature software engineering practices for that era.

The application implements a complete online storefront with product catalog browsing, shopping basket functionality, customer account management, order processing, and payment integration with PayPal. The architecture exhibits excellent separation of concerns through a 5-layer structure: Presentation (ASP.NET MVC), Business Logic (Services), Domain Model, Data Access (NHibernate), and Infrastructure (cross-cutting concerns).

Despite being built with now-legacy technologies, the codebase demonstrates high-quality architectural patterns including Repository pattern, Unit of Work, Dependency Injection (StructureMap), Domain Events, Factory pattern, and State pattern. The strong architectural foundation provides a solid base for modernization efforts, though significant technology upgrades are required to address obsolescence and security concerns.

Technology Stack Summary: - Platform: .NET Framework 3.5 / 4.0 - Language: C# 3.5 / 4.0 - Architecture Style: Layered Architecture with Domain-Driven Design (N-Tier Monolith) - Database: SQL Server Express LocalDB (User Instance mode) - ORM: NHibernate 2.1 with HBM.XML mappings - Client Technology: ASP.NET MVC 2, ASPX Views, jQuery 1.3.2 - Integration: HTTP POST (PayPal), OAuth-style callback (Janrain), SMTP (Email) - Dependency Injection: StructureMap 2.5

External Dependencies Description

PayPal Payment Gateway
  • Purpose: Secure credit card payment processing for customer orders
  • Integration Protocol: HTTPS Form POST redirect
  • Data Format: HTML form fields (item details, prices, return URLs)
  • Frequency: On-demand (per order checkout)
  • Authentication: Business email configuration in Web.config
  • Criticality: Critical - required for order completion and revenue collection
  • Implementation: Located in Agathas.Storefront.Infrastructure/Payments/PaypalPaymentService.cs
  • Endpoint: https://www.sandbox.paypal.com/cgi-bin/webscr (sandbox mode)
Janrain Authentication Provider
  • Purpose: External authentication via social login providers (Facebook, Google, Twitter)
  • Integration Protocol: OAuth-style authentication callback
  • Data Format: Query parameters with authentication token
  • Frequency: On-demand (user login/registration)
  • Authentication: API key configured in Web.config
  • Criticality: High - provides alternative authentication method to reduce registration friction
  • Implementation: Located in Agathas.Storefront.Infrastructure/Authentication/JanrainAuthenticationService.cs
SMTP Email Server
  • Purpose: Transactional email delivery (order confirmations, receipts, notifications)
  • Integration Protocol: SMTP
  • Data Format: MIME email messages
  • Frequency: On-demand (triggered by business events)
  • Authentication: Username/password configured in Web.config mailSettings
  • Criticality: Medium - important for customer communication but not blocking
  • Implementation: Located in Agathas.Storefront.Infrastructure/Email/SmtpEmailService.cs with TextLoggingEmailService.cs fallback for development
SQL Server Express LocalDB
  • Type: Relational Database Management System
  • Purpose: Primary data store for all application data (products, orders, customers, baskets)
  • Access Pattern: Via NHibernate ORM with HBM.XML mappings
  • Backup Strategy: User Instance attach/detach model with MDF files in App_Data folder
  • Connection: AttachDbFilename with User Instance=true
  • Database Files:
  • App_Data\Shop.mdf - Main application database
  • App_Data\aspnetdb.mdf - ASP.NET Membership database

Container Details

ASP.NET MVC Web Application
  • Technology: ASP.NET MVC 2.0 on .NET Framework 4.0
  • Purpose: Web hosting container serving HTML pages to customers and administrators
  • Hosting: IIS 7.0+ or IIS Express
  • Responsibilities:
  • HTTP request/response handling
  • Routing configuration (Global.asax.cs)
  • Static content delivery (CSS, JavaScript, images)
  • Dependency injection bootstrapping via StructureMap
  • Global application configuration
  • Session state management
  • Key Files:
  • Global.asax.cs - Application startup and routing
  • Web.config - Configuration settings
  • Views/ - ASPX view templates
  • Content/ - CSS and images
  • Scripts/ - jQuery JavaScript files
  • Location: Agathas.Storefront.UI.Web.MVC project
Controllers Layer
  • Technology: ASP.NET MVC 2.0 / C# 3.5
  • Purpose: Handles HTTP requests, prepares view models, coordinates with services
  • Hosting: Loaded by MVC Web Application container
  • Responsibilities:
  • MVC controller implementations (9 controllers, ~30 endpoints)
  • View model definitions for presentation layer
  • Action argument handling and model binding
  • JSON DTOs for AJAX endpoints
  • AutoMapper configuration for controller mappings
  • Custom IoC controller factory
  • Controllers:
  • HomeController - Landing page and featured products
  • ProductController - Product catalog and search
  • BasketController - Shopping basket operations
  • CheckoutController - Order checkout flow
  • PaymentController - Payment processing callbacks
  • OrderController - Order history and details
  • CustomerController - Account management
  • AccountLogOnController - User authentication
  • AccountRegisterController - User registration
  • Location: Agathas.Storefront.Controllers project
Business Services Layer
  • Technology: C# 3.5 / AutoMapper 1.0
  • Purpose: Implements business use cases and workflows with request/response messaging
  • Hosting: Instantiated by controllers via dependency injection
  • Responsibilities:
  • Business logic orchestration
  • Request/response message processing (CQRS-style)
  • Domain entity to view model mapping
  • Domain event handler registration
  • Transaction coordination via Unit of Work
  • Service-level validation
  • Services:
  • IProductCatalogService - Product browsing, search, filtering
  • IBasketService - Shopping basket management
  • IOrderService - Order submission and retrieval
  • ICustomerService - Customer account operations
  • Messaging Pattern: Request objects (e.g., GetProductsByCategoryRequest) → Service → Response objects (e.g., GetProductsByCategoryResponse)
  • Location: Agathas.Storefront.Services and Agathas.Storefront.Services.Cache projects
Domain Model Layer
  • Technology: C# 3.5 / Domain-Driven Design patterns
  • Purpose: Core business logic encapsulated in rich domain entities and aggregates
  • Hosting: Referenced by Services and Data Access layers
  • Responsibilities:
  • Domain entities and aggregate roots (Basket, Order, Customer, Product)
  • Business rules and invariant enforcement
  • Domain events (e.g., OrderSubmittedEvent)
  • Repository interfaces (IBasketRepository, IOrderRepository, etc.)
  • Value objects (Address, Payment)
  • Domain services (ShippingService)
  • State pattern implementations (IOrderState, OpenOrderState, SubmittedOrderState)
  • Key Aggregates:
  • Basket Aggregate - Shopping basket with basket items
  • Order Aggregate - Order with order items, payment, delivery address
  • Customer Aggregate - Customer with delivery addresses
  • Product Aggregate - Product title with product variants (sizes, colors)
  • Location: Agathas.Storefront.Model project
Data Access Layer
  • Technology: NHibernate 2.1 / C# 3.5 / HBM.XML mappings
  • Purpose: Abstracts database access through Repository pattern implementations
  • Hosting: Instantiated by services via dependency injection
  • Responsibilities:
  • Repository pattern implementations
  • NHibernate session factory configuration
  • HBM.XML mapping files for OR/M
  • Unit of Work implementation (NHUnitOfWork)
  • Query translation to NHibernate criteria
  • Session storage (HTTP and thread-based)
  • Connection management
  • Technologies:
  • NHibernate 2.1.0.2002
  • LinFu 1.0.3 (lazy loading proxies)
  • Iesi.Collections 1.0.1 (NHibernate collections)
  • Location: Agathas.Storefront.Repository.NHibernate project
Infrastructure Layer
  • Technology: C# 3.5 / Log4Net 1.2.10 / StructureMap 2.5
  • Purpose: Provides cross-cutting concerns and technical services
  • Hosting: Referenced by all other layers
  • Responsibilities:
  • Authentication: Forms Authentication, ASP.NET Membership, Janrain integration
  • Logging: Log4Net adapter with file appender
  • Configuration: Application settings management
  • Email: SMTP service and text logging fallback
  • Payments: PayPal integration service
  • Cookie Storage: Cookie-based data storage
  • Domain Base Classes: EntityBase, ValueObjectBase, AggregateRoot
  • Domain Events Infrastructure: Static DomainEvents class
  • Repository Abstractions: IRepository, IUnitOfWork
  • Querying: Query object abstractions
  • Location: Agathas.Storefront.Infrastructure project
Shop Database
  • Technology: SQL Server Express LocalDB (User Instance mode)
  • Purpose: Primary application data storage
  • Size: Unknown (static analysis cannot determine actual database size)
  • Key Tables: Product, ProductTitle, Basket, BasketItem, Order, OrderItem, Customer, DeliveryAddress, Payment, Category, Brand
  • Access Pattern: Via NHibernate ORM with Unit of Work per HTTP request
  • Backup: User Instance attach/detach via MDF file
  • Connection String: AttachDbFilename=|DataDirectory|Shop.mdf;Integrated Security=True;User Instance=True
Membership Database
  • Technology: SQL Server Express LocalDB (User Instance mode)
  • Purpose: ASP.NET Membership authentication and user profile storage
  • Tables: aspnet_Users, aspnet_Membership, aspnet_Profile
  • Access Pattern: Via ASP.NET Membership Provider
  • Connection String: Separate connection for membership provider

Inter-Container Communication

Communication Patterns: - Synchronous: All communication is synchronous method calls within the monolithic process - Asynchronous: None - no message queues or async processing - Event-Driven: Domain Events within same process (not distributed events)

Protocols Used: - Internal: Direct method calls via dependency injection - External HTTP/HTTPS: PayPal (Form POST), Janrain (OAuth callback), SMTP - Database: ADO.NET via NHibernate ORM (SQL protocol)

Dependency Flow: - Presentation → Business Services → Domain → Data Access → Infrastructure - Unidirectional dependencies (no circular references) - Infrastructure layer has no dependencies on application layers

Hosting and Deployment: - Environment: On-premises IIS or development IIS Express - Deployment Model: Single monolithic deployment (XCOPY or Web Deploy) - Orchestration: None - traditional web application hosting - Load Balancing: Requires external load balancer (not implemented in application) - Session Affinity: Required if session state used (current implementation uses cookies)

Code Flow Description

Typical Request Flow (Add Item to Basket Example):

  1. Request Entry - HTTP POST request arrives at BasketController.Add(productId)
  2. Authentication - [Authorize] attribute verifies Forms Authentication cookie
  3. Model Binding - MVC model binder creates AddItemToBasketRequest from form/query parameters
  4. Validation - Model validation attributes checked (e.g., [Required], [Range])
  5. Service Invocation - Controller calls IBasketService.AddItemToBasket(request)
  6. Data Retrieval - Service fetches Basket and Product entities via repositories
  7. Business Logic - Domain entity Basket.AddItem() method enforces business rules
  8. Persistence - Repository saves changes through NHibernate session
  9. Transaction Commit - Unit of Work commits transaction to database
  10. Response - Controller returns redirect to basket view

Error Handling Strategy:

  • Validation Errors - Caught by MVC model validation, returns 400 Bad Request or re-displays form with errors
  • Business Rule Violations - Domain entities throw DomainException, caught by controller, displayed as user-friendly message
  • Data Access Errors - NHibernate exceptions caught by service layer, logged via Log4Net, returns 500 Internal Server Error
  • External Service Failures - PayPal/Janrain failures caught, logged, display error page to user
  • Unhandled Exceptions - Global exception filter in Global.asax logs and displays generic error page

Error Response Format: - Web Requests - HTML error pages or model validation errors displayed in form - AJAX Requests - JSON responses with { success: false, message: "Error description" }

Logging Strategy: - Info - Successful operations (order submitted, user registered) - Warning - Recoverable errors (validation failures, external service timeouts) - Error - Exceptions requiring attention (database errors, integration failures) - Debug - Detailed execution flow (enabled in development only) - Log Location - File system at C:\logs\ via Log4Net RollingFileAppender

Transaction Management:

  • Scope - One NHibernate session per HTTP request
  • Isolation Level - Read Committed (SQL Server default)
  • Commit Strategy - Explicit UnitOfWork.Commit() called by service layer after successful business logic execution
  • Rollback Strategy - Automatic rollback on exception (session disposed without commit)
  • Long-Running Transactions - Not used; transactions are short-lived within single HTTP request
  • Distributed Transactions - Not implemented (single database)

4. Unit of Work Pattern

Description: Transaction management centralized in IUnitOfWork implementation wrapping NHibernate session lifecycle. Ensures all repository operations within single request participate in same transaction.

Implementation: 

public interface IUnitOfWork
{
    ISession GetSession();
    void Commit();
    void Rollback();
}

public class NHUnitOfWork : IUnitOfWork
{
    private readonly ISession _session;

    public void Commit()
    {
        using (var transaction = _session.BeginTransaction())
        {
            transaction.Commit();
        }
    }
}

Scope: Per HTTP request (session stored in HttpContext)

Benefits: - ✅ Consistent transaction management - ✅ Automatic rollback on errors - ✅ Single database round-trip for multiple operations - ✅ Clear transaction boundaries

Trade-offs: - ⚠️ Must remember to call Commit() - ⚠️ Long-running requests hold transactions

Context: The application uses SQL Server Express LocalDB with User Instance mode for both main application database (Shop.mdf) and ASP.NET Membership database (aspnetdb.mdf). Files are stored in App_Data\ folder with AttachDbFilename and User Instance=true connection string parameters.

Decision: Use SQL Server Express LocalDB User Instance mode for development and deployment simplicity.

Original Rationale (circa 2010): - Zero-configuration database deployment - XCOPY deployment with database files - No separate SQL Server installation required - Suitable for small-scale deployments - Good for development and testing

Consequences: - ✅ Positive (Original): - Simple deployment (just copy MDF files) - No DBA required for initial setup - Works out of the box for development

  • ⚠️ Neutral/Trade-offs:
  • File-based database limits concurrent access

  • No central management or monitoring

  • ❌ Negative (Current Critical Issues):

  • User Instance feature deprecated in SQL Server 2012 and removed in 2014
  • Not suitable for production workloads (performance, reliability, scalability)
  • No backup/restore capabilities for production
  • Single point of failure (no redundancy)
  • Connection string exposes full file path
  • Difficult to scale horizontally
  • No connection pooling optimization possible
  • Cannot support multiple application instances

Alternatives (Must Consider): 1. SQL Server Express (Standard Instance): Shared SQL Server instance for multi-app support 2. SQL Server Standard/Enterprise: Production-grade SQL Server for high availability 3. Azure SQL Database: Managed cloud database with auto-scaling, backup, geo-replication 4. Cloud Database Alternatives: AWS RDS, Google Cloud SQL for managed SQL Server

Implementation Notes: - Current connection strings: AttachDbFilename=|DataDirectory|Shop.mdf;Integrated Security=True;User Instance=True - Database files in Agathas.Storefront.UI.Web.MVC\App_Data\ - No migration scripts (schema embedded in HBM.XML mappings)

Migration Path: 1. Immediate: Switch to SQL Server Express standard instance (eliminate User Instance) 2. Short-term: Implement proper database versioning and migration scripts 3. Long-term: Migrate to managed cloud database service (Azure SQL, AWS RDS)

Related ADRs: - ADR-002 (NHibernate as ORM) - Connection string changes needed - ADR-015 (Cloud Migration Strategy) - Cloud database selection

ADR-008: Domain Events with Static Class

Status: Accepted (with caveats)

Context: Need for decoupling between domain layer and infrastructure services (e.g., sending email when order is submitted) without creating dependencies from domain to infrastructure.

Decision: Implement domain events pattern using static DomainEvents class with publish/subscribe mechanism.

Rationale: - Domain entities can raise events without knowing who handles them - Infrastructure registers event handlers at application startup - Keeps domain layer clean (no infrastructure dependencies) - Simple implementation without external event bus - Events processed synchronously in same transaction

Implementation: 

// Static domain events class
public static class DomainEvents
{
    private static List<Delegate> _handlers = new List<Delegate>();

    public static void Register<T>(Action<T> handler) where T : IDomainEvent
    {
        _handlers.Add(handler);
    }

    public static void Raise<T>(T domainEvent) where T : IDomainEvent
    {
        foreach (var handler in _handlers.OfType<Action<T>>())
        {
            handler(domainEvent);
        }
    }
}

// Usage in domain entity
public class Order
{
    public void Submit()
    {
        // ... business logic ...
        DomainEvents.Raise(new OrderSubmittedEvent(this));
    }
}

// Handler registered in service layer
DomainEvents.Register<OrderSubmittedEvent>(e => 
    _emailService.SendOrderConfirmation(e.Order));

Consequences: - ✅ Positive: - Domain layer remains infrastructure-agnostic - Easy to add new event handlers without changing domain - Events processed in same transaction as domain changes - Simple implementation without external dependencies

  • ⚠️ Neutral/Trade-offs:
  • Static class can complicate unit testing (requires setup/teardown)
  • No ordering guarantees for multiple handlers

  • Synchronous processing (blocks request thread)

  • ❌ Negative:

  • Not suitable for distributed events or microservices
  • No retry or error handling for failed handlers
  • Tight coupling to single process (cannot scale event processing)

Alternatives Considered: 1. MediatR Library: Not available/popular in 2010; now excellent alternative 2. Service Bus (e.g., NServiceBus): Over-engineering for in-process events 3. Observer Pattern with Interfaces: More boilerplate, similar limitations

Current Status: ACCEPTABLE FOR MONOLITH - Works well for current architecture; consider MediatR during modernization

Modernization Recommendation: - Migrate to MediatR for better testability and flexibility - Consider distributed event bus (Azure Service Bus, RabbitMQ) if extracting microservices

ADR-009: ASPX View Engine (WebForms Views)

Status: Superseded (by Razor in modern .NET)

Context: ASP.NET MVC 2 supported both ASPX (WebForms) view engine and Spark view engine. Razor was introduced in MVC 3.

Decision: Use ASPX view engine for rendering HTML views.

Rationale (circa 2010): - Default view engine in ASP.NET MVC 2 - Familiar syntax for developers transitioning from WebForms - Mature and well-documented - Strong tooling support in Visual Studio

Consequences: - ✅ Positive (Original): - Immediate productivity (no learning curve) - IntelliSense support in Visual Studio - Familiar <% %> syntax

  • ❌ Negative (Current):
  • Verbose syntax compared to Razor (<% %> vs @)
  • Difficult to test (views are compiled at runtime)
  • No compile-time checking of view code
  • Obsolete technology (Razor is standard since MVC 3, released 2011)

Alternatives (Modern): 1. Razor View Engine: Clean syntax, compile-time checking, strong typing 2. Blazor: Component-based UI with C# (for modern rewrite) 3. SPA Framework (React/Angular/Vue): Decoupled frontend

Migration Path: - Short-term: Migrate to Razor views during ASP.NET MVC upgrade - Long-term: Consider SPA architecture with API backend

ADR-010: No Caching Implementation

Status: Deferred (Caching designed but not enabled)

Context: Product catalog is read-heavy with relatively static data. Performance optimization through caching was considered.

Decision: Caching decorator CachedProductCatalogService was implemented but not activated in IoC configuration.

Evidence: - File exists: Agathas.Storefront.Services.Cache/CachedProductCatalogService.cs - Decorator pattern implemented around IProductCatalogService - NOT registered in StructureMap BootStrapper (regular ProductCatalogService used instead)

Why Deferred: - Insufficient production load data to determine caching strategy - Concerns about cache invalidation complexity - Product data changes infrequently (could use long cache TTL) - Premature optimization without performance problems

Consequences: - ✅ Positive: - Simpler implementation (no cache invalidation logic needed) - No stale data issues - Easy to debug (no cache-related bugs)

  • ❌ Negative:
  • Database hit for every product catalog request
  • Higher database load
  • Slower response times for product browsing
  • Increased infrastructure costs

Recommendation: - Enable caching during modernization with proper strategy: - Distributed cache (Redis/Memcached) for horizontal scaling - Cache product catalog data (categories, products, brands) - Time-based expiration (e.g., 15-30 minutes) - Event-based invalidation when products updated - Output caching for static HTML pages
