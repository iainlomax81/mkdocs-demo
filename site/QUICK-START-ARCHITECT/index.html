Current Architecture (C4 Level 2 - Container Diagram)

5-Tier Layered Architecture with unidirectional dependencies:

Layer Details

1. Presentation Layer (Agathas.Storefront.UI.Web.MVC) - Technology: ASP.NET MVC 2, ASPX views, jQuery 1.3.2 - Responsibilities: HTTP handling, routing, view rendering, static content - Key Components: Global.asax, Web.config, Views, Content, Scripts - Issues: Non-responsive design, outdated jQuery (CVEs), ASPX views (obsolete) - Evidence: System Architecture - Container Diagram

2. Controllers Layer (Agathas.Storefront.Controllers) - Technology: ASP.NET MVC 2 controllers, AutoMapper 1.1 - Responsibilities: Request handling, view model mapping, action filters - Controllers: 9 controllers (~30 endpoints) - HomeController, ProductController, BasketController - CheckoutController, PaymentController, OrderController - CustomerController, AccountLogOnController, AccountRegisterController - Pattern: Request/Response messaging with services layer - Evidence: api-catalog.json

3. Services Layer (Agathas.Storefront.Services) - Technology: C# 3.5, AutoMapper 1.1 - Responsibilities: Business logic orchestration, cross-aggregate coordination - Services: 4 primary services - ProductService, BasketService, OrderService, CustomerService - Pattern: Request/Response objects, domain event publishing - Evidence: Business Services

4. Domain Layer (Agathas.Storefront.Model) - Technology: C# 3.5 pure domain logic (no framework dependencies) - Responsibilities: Business rules, invariants, domain events - Aggregates: 4 aggregate roots - ProductTitle (product catalog) - Basket (shopping cart) - Order (placed orders) - Customer (customer accounts) - Patterns: DDD (entities, value objects, aggregates), State Pattern (Order lifecycle) - Business Rules: 40+ documented rules enforced in domain - Strengths: ⭐⭐⭐⭐⭐ Excellent DDD implementation - Evidence: Business Domain Model

5. Data Access Layer (Agathas.Storefront.Repository.NHibernate) - Technology: NHibernate 2.1, HBM.XML mappings - Responsibilities: Repository implementations, ORM mapping, persistence - Repositories: ProductRepository, BasketRepository, OrderRepository, CustomerRepository - Pattern: Repository Pattern, Unit of Work Pattern - Issues: Lazy loading throughout (N+1 query risk), outdated NHibernate version - Evidence: Data Architecture

6. Infrastructure Layer (Agathas.Storefront.Infrastructure) - Technology: C# 3.5, Log4Net 1.2, StructureMap 2.5 - Responsibilities: Cross-cutting concerns (auth, logging, email, payments, configuration) - Components: - Authentication (Forms Auth, Janrain) - Logging (Log4Net file appender) - Email (SMTP, TextLogging fallback) - Payments (PayPal integration) - Configuration management - Dependency injection (StructureMap) - Evidence: System Architecture - Infrastructure

Current State Strengths (Preserve During Modernization)

✅ Excellent Domain-Driven Design: - Clean aggregate boundaries with well-defined roots - Rich domain entities with encapsulated business logic - Value objects for addresses, payments, product attributes - Domain events infrastructure (underutilized but present) - Preservation Strategy: Keep domain model intact, migrate to .NET 6+ with minimal changes

✅ Clean Architectural Patterns: - Repository Pattern with interface abstractions - Unit of Work for transaction management - Dependency Injection throughout (StructureMap) - State Pattern for order lifecycle - Factory Pattern for controller creation - Preservation Strategy: Maintain patterns, update implementation (EF Core, built-in DI)

✅ Testable Design: - Interface-based abstractions - Pure domain logic (no framework coupling) - DI enables test doubles - Opportunity: Zero tests currently, but architecture makes testing straightforward

✅ Business Logic Completeness: - Complete e-commerce workflows implemented - 40+ business rules documented and enforced - PCI DSS compliant payment integration - Preservation Strategy: Keep business logic, enhance with missing features (inventory, returns)

Current State Constraints (Must Address)

❌ Technology Obsolescence (CRITICAL): - .NET Framework 3.5/4.0: Out of support, no security patches - ASP.NET MVC 2: 15+ years old, superseded by ASP.NET Core - jQuery 1.3.2: Multiple CVEs (XSS vulnerabilities) - NHibernate 2.1: Outdated, lacks modern features - Impact: Security risk, recruitment difficulty, cannot leverage modern capabilities

❌ Scalability Blockers (HIGH): - In-process session state (<sessionState mode="InProc" />) - LocalDB User Instance mode (requires local file system) - File-based logging (C:\logs\ directory) - No distributed caching (first-level cache only) - Impact: Cannot scale horizontally, single point of failure

❌ Security Vulnerabilities (CRITICAL): - Plaintext secrets in Web.config (connection strings, SMTP credentials, PayPal API key) - jQuery 1.3.2 XSS vulnerabilities (CVE-2011-4969, CVE-2012-6708, CVE-2015-9251) - ASP.NET Membership with weak SHA1 hashing - No input validation framework - Impact: Data breach risk, compliance violations

❌ Compliance Gaps (HIGH for EU customers): - No GDPR data subject rights (erasure, access, portability) - No consent management (cookie banner) - No privacy controls - Impact: Fines up to 4% revenue or €20M

❌ Operational Limitations (MEDIUM): - No automated testing (0% coverage) - Manual deployment (hours, error-prone) - No CI/CD pipeline - File-based logging only (no APM, no metrics) - Impact: Slow development cycles, high defect risk, limited observability

📝 Architecture Decision Records (ADRs)

ADR-001: Incremental Modernization vs Big-Bang Rewrite

Status: ✅ ACCEPTED
Date: 2026-06-09
Deciders: Architecture team, executive sponsor

Context: Agathas.Storefront requires technology modernization due to obsolete stack (15+ years old). Two primary approaches considered: 1. Big-Bang Rewrite: Complete system replacement from scratch 2. Incremental Modernization: Phased approach preserving domain model

Current Problem: - Technology stack obsolete (.NET Framework 3.5/4.0, no security patches) - Cannot scale horizontally (in-process state, LocalDB) - Security vulnerabilities (jQuery CVEs, plaintext secrets) - GDPR non-compliance (if serving EU customers) - Non-responsive design (mobile users 70%+ of traffic)

Decision: Incremental Modernization with phased approach

Alternatives Considered:

Option A: Big-Bang Rewrite - ✅ Pros: Clean slate, no legacy constraints, latest technologies from day one - ❌ Cons: - High risk: Complete replacement with no fallback - Long cycle: 12-18+ months typical for full rewrites - No incremental value: No business benefit until cutover - Knowledge loss: Risk of losing business rules during recreation - Maintenance burden: Must maintain both old and new systems during development - ⚠️ Cost: Higher total cost (dual maintenance, extended timeline, risk mitigation) - ⚠️ Complexity: HIGH - entire system recreation from scratch

Option B: Incremental Modernization (SELECTED) - ✅ Pros: - Lower risk: Smaller changes, easier to test and rollback - Incremental value: Each phase delivers business benefit - Preserve assets: Excellent domain model retained (no recreation) - Business continuity: System remains operational throughout - Learn and adapt: Adjust approach based on early phases - ❌ Cons: - Longer overall timeline: Phased approach may extend calendar time - Technical debt: Must live with some legacy during transition - Integration complexity: New and old components coexist temporarily - ⚠️ Cost: Lower total cost (single system maintenance, reduced risk, faster value delivery) - ⚠️ Complexity: MEDIUM - requires careful sequencing and integration

Decision Criteria: - Business risk tolerance: MEDIUM (cannot afford complete outage) - Time to first value: HIGH priority (need security fixes soon) - Domain model quality: EXCELLENT (4.5/5 - worth preserving) - Business continuity requirement: CRITICAL

Decision Matrix:

Criterion Weight Big-Bang Rewrite Incremental Selected
Business Risk HIGH (×3) LOW (3) = 9 HIGH (9) = 27 Incremental
Time to Value HIGH (×3) LOW (3) = 9 HIGH (9) = 27 Incremental
Preserve Domain Model MEDIUM (×2) LOW (3) = 6 HIGH (9) = 18 Incremental
Technical Cleanliness LOW (×1) HIGH (9) = 9 MEDIUM (5) = 5 Big-Bang
Total 33 77 Incremental

Rationale: - Domain Model Excellence: The current domain model (DDD with 4 aggregates, 40+ business rules) is well-implemented and would be costly to recreate. Preservation saves months of effort and reduces risk of business logic loss. - Business Continuity: Incremental approach keeps system operational, avoiding revenue loss during extended rewrite period. - Risk Management: Smaller changes in each phase reduce risk of catastrophic failure. Can rollback individual phases without losing entire investment. - Value Delivery: Early phases (testing, security fixes, scalability) deliver measurable business value within weeks/months, not waiting 12-18+ months for big-bang cutover.

Consequences: - ✅ Positive: Lower risk, faster time to first value, preserved domain expertise, business continuity - ❌ Negative: Longer overall calendar time, temporary coexistence of old/new patterns, ongoing refactoring - ⚠️ Risks: Phase dependencies could delay later phases if earlier phases discover unexpected complexity

Validation: - Success Metrics: - Phase 1 completion within 2-4 months of start (velocity-dependent) - Zero production incidents caused by modernization changes - Test coverage >60% by Phase 1 end - Critical vulnerabilities eliminated by Phase 1 end - Review Timeline: After each phase completion, assess approach and adjust if needed

References: - Strangler Fig Pattern - Martin Fowler - EXECUTIVE-SUMMARY.md - Phased approach details

ADR-002: Cloud Platform Approach (Vendor-Agnostic)

Status: ✅ ACCEPTED (vendor-agnostic architecture)
Date: 2026-06-09
Deciders: Architecture team

Context: Target architecture requires cloud-native capabilities (managed database, auto-scaling, distributed caching, secrets management, APM). Cloud provider selection will be made by business stakeholders, so architecture must support multiple vendors.

Decision: Design vendor-agnostic architecture compatible with Azure, AWS, and GCP

Alternatives Considered:

Option A: Azure-Specific Design - ✅ Pros: Native Windows/.NET support, seamless integration with existing Microsoft stack - ❌ Cons: Vendor lock-in, migration cost if switching providers, limits negotiation leverage - ⚠️ Cost: Azure pricing competitive for .NET workloads, but locked into Azure pricing model - ⚠️ Complexity: LOW - natural fit for .NET applications

Option B: AWS-Specific Design - ✅ Pros: Market leader, broadest service catalog, mature ecosystem - ❌ Cons: .NET support secondary to Java/Node, more AWS-specific services used - ⚠️ Cost: AWS pricing typically higher for equivalent services, negotiable at scale - ⚠️ Complexity: MEDIUM - less .NET-native tooling than Azure

Option C: GCP-Specific Design - ✅ Pros: Competitive pricing, excellent Kubernetes support, strong data/ML services - ❌ Cons: Smallest market share, less .NET-specific tooling - ⚠️ Cost: GCP pricing often most competitive, committed use discounts - ⚠️ Complexity: MEDIUM - similar to AWS for .NET workloads

Option D: Vendor-Agnostic Design (SELECTED) - ✅ Pros: - Portability: Can switch providers if needed - Negotiation leverage: Multi-cloud strategy enables better pricing - Technology choices: Use best-of-breed services regardless of vendor - Risk mitigation: Not dependent on single vendor viability - ❌ Cons: - Abstraction overhead: Must avoid vendor-specific features - Potential cost premium: May not leverage vendor-specific optimizations - ⚠️ Cost: Comparable across vendors for standard services (compute, database, cache) - ⚠️ Complexity: MEDIUM - requires abstraction layer for provider differences

Decision Criteria: - Portability: HIGH priority (avoid lock-in) - Business flexibility: HIGH priority (enable multi-vendor strategy) - Technology choice: MEDIUM priority (prefer open standards) - Optimization: LOW priority (portability > vendor-specific optimizations)

Rationale: - Business Strategy: Cloud provider not yet selected by stakeholders. Vendor-agnostic design preserves flexibility for business negotiations and decisions. - Technology Standards: Use open standards (Docker, Kubernetes, Redis, OpenTelemetry, OAuth/OIDC) that work across all major cloud providers. - Risk Mitigation: Avoid dependencies on vendor-specific services (e.g., avoid Azure Functions, AWS Lambda, GCP Cloud Functions - use standard containers instead). - Portability: If business requirements change or pricing becomes unfavorable, can migrate to different provider without architectural redesign.

Implementation Approach:

Common Services Across Vendors: | Service Type | Open Standard / Common Implementation | Azure | AWS | GCP | |--------------|--------------------------------------|-------|-----|-----| | Containers | Docker, Kubernetes | Azure Container Apps, AKS | ECS, EKS | Cloud Run, GKE | | Database | PostgreSQL or SQL Server | Azure Database for PostgreSQL, Azure SQL | RDS PostgreSQL, RDS SQL Server | Cloud SQL PostgreSQL, Cloud SQL SQL Server | | Cache | Redis | Azure Cache for Redis | ElastiCache for Redis | Memorystore for Redis | | Secrets | Environment variables + vault | Azure Key Vault | AWS Secrets Manager | Secret Manager | | Logging | Structured JSON logs | Application Insights | CloudWatch | Cloud Logging | | Monitoring | OpenTelemetry | Application Insights | CloudWatch + X-Ray | Cloud Monitoring + Trace | | CDN | Standard HTTP cache | Azure CDN | CloudFront | Cloud CDN |

Consequences: - ✅ Positive: Business flexibility, negotiation leverage, portability, risk mitigation - ❌ Negative: Cannot use vendor-specific optimizations, abstraction overhead - ⚠️ Risks: May miss vendor-specific features that could provide competitive advantage

Validation: - Success Metrics: Architecture diagrams and documentation reference generic services, not vendor-specific products - Proof of Concept: Deploy containerized application to 2+ cloud providers to validate portability

ADR-003: Migration from NHibernate to Entity Framework Core

Status: ✅ ACCEPTED
Date: 2026-06-09
Deciders: Architecture team

Context: Current application uses NHibernate 2.1 (2009) with XML-based HBM mappings. Modernization to .NET 6+ provides opportunity to migrate to Entity Framework Core, which is Microsoft's recommended ORM for .NET Core/.NET 6+.

Decision: Migrate to Entity Framework Core 6+ with code-first Fluent API

Alternatives Considered:

Option A: Keep NHibernate 2.1 - ✅ Pros: No migration effort, existing mappings work - ❌ Cons: Severely outdated (13+ years old), lacks modern features, community support declining - ⚠️ Effort: ZERO - no changes required - ⚠️ Risk: HIGH - outdated ORM limits modernization, potential bugs, no support

Option B: Upgrade NHibernate to 5.x - ✅ Pros: Keeps familiar ORM, incremental upgrade path, improved performance - ❌ Cons: Still requires HBM.XML migration to Fluent mapping, not Microsoft-supported, smaller community than EF Core - ⚠️ Effort: MEDIUM - XML→Fluent mapping conversion, testing, NHibernate 2→5 breaking changes - ⚠️ Risk: MEDIUM - Third-party dependency, community support < EF Core

Option C: Entity Framework Core 6+ (SELECTED) - ✅ Pros: - Microsoft-supported with active development - Native .NET 6+ integration - Code-first with Fluent API (modern approach) - Excellent tooling (migrations, database scaffolding) - Large community and extensive documentation - Performance on par with NHibernate 5.x - ❌ Cons: - Migration effort required (HBM.XML → Fluent API) - Learning curve for team (if unfamiliar with EF Core) - Some NHibernate features not in EF Core (criteria API differences) - ⚠️ Effort: MEDIUM-HIGH - Mapping conversion, repository updates, query refactoring, comprehensive testing - ⚠️ Risk: MEDIUM - Well-documented migration path, comprehensive testing required

Decision Criteria: - Microsoft support: HIGH importance (future-proof) - Community size: MEDIUM importance (resources, troubleshooting) - Modern features: HIGH importance (migrations, tooling) - Migration effort: MEDIUM importance (necessary investment for long-term benefit)

Decision Matrix:

Microsoft Support HIGH (×3) LOW (1) = 3 LOW (3) = 9 HIGH (9) = 27 EF Core
Modern Features HIGH (×3) LOW (1) = 3 MEDIUM (5) = 15 HIGH (9) = 27 EF Core

Total 30 44 82 EF Core

Rationale: - Microsoft Support: EF Core is first-class citizen in .NET 6+ ecosystem with guaranteed long-term support - Modern Features: Code-first approach with migrations simplifies schema evolution, better tooling integration - Community: Largest .NET ORM community, extensive documentation, Stack Overflow support - Performance: EF Core 6+ performance comparable to NHibernate 5.x (Microsoft benchmarks) - Investment: Migration effort justified by long-term maintainability and modern features

Migration Strategy:

Phase 1: Repository Layer Isolation (DONE - current architecture) - Repository Pattern already abstracts ORM from domain - Domain layer has no NHibernate dependencies

Phase 2: Entity Mapping Conversion - Convert HBM.XML mappings → EF Core Fluent API configurations - Maintain identical database schema (no schema changes) - Example mapping translation: 

// Current: HBM.XML
<class name="Product" table="Products">
  <id name="Id" column="ProductId">
    <generator class="identity" />
  </id>
  <property name="Name" column="ProductName" />
</class>

// Target: EF Core Fluent API
public class ProductConfiguration : IEntityTypeConfiguration<Product>
{
    public void Configure(EntityTypeBuilder<Product> builder)
    {
        builder.ToTable("Products");
        builder.HasKey(p => p.Id);
        builder.Property(p => p.Id).HasColumnName("ProductId").ValueGeneratedOnAdd();
        builder.Property(p => p.Name).HasColumnName("ProductName");
    }
}

Phase 3: Repository Implementation Update - Replace NHibernate ISession with EF Core DbContext - Update repository implementations to use EF Core APIs - Convert NHibernate criteria queries to LINQ (EF Core query provider)

Phase 4: Testing - Unit tests for repository layer - Integration tests against test database - Data integrity validation (query results match NH vs EF Core)

Consequences: - ✅ Positive: Modern ORM, Microsoft support, tooling integration, future-proof - ❌ Negative: Migration effort (estimated 2-4 weeks for mapping conversion + testing) - ⚠️ Risks: Query behavior differences between NH and EF Core require thorough testing

Validation: - Success Metrics: - All 15 entities successfully mapped in EF Core - All repository integration tests passing - Query performance within 10% of NHibernate baseline - Zero data integrity issues in QA environment - Testing Approach: Side-by-side testing (NH vs EF Core) to validate query results match

References: - Entity Framework Core Documentation - EF Core vs NHibernate Comparison

🔄 Migration Patterns & Strategies

Primary Pattern: Strangler Fig Pattern

Pattern Description: Incrementally replace parts of the legacy system by placing a façade in front, routing requests to either legacy or new implementation, gradually "strangling" the old system until it can be retired.

Named After: Strangler fig tree that grows around host tree, eventually replacing it entirely.

How It Works: 1. Create façade/routing layer that intercepts all requests 2. Implement new functionality alongside old (parallel) 3. Route specific requests to new implementation 4. Test thoroughly with production traffic (canary/blue-green) 5. Gradually expand new implementation scope 6. Remove old implementation when fully replaced 7. Repeat for next component

Why Chosen for Agathas.Storefront: - ✅ Low risk: Old system remains operational as fallback - ✅ Incremental value: Each migrated component delivers benefit - ✅ Testable: Can validate new implementation with real traffic before full cutover - ✅ Reversible: Can route back to old implementation if issues arise - ✅ Business continuity: Zero downtime during migration

Implementation for Agathas: Strangler Fig applied at technology layer level (not microservices decomposition - that's out of scope for initial modernization):

  1. Phase 1: Strangle infrastructure dependencies
  2. Session state: In-process → distributed cache
  3. Logging: File-based → structured cloud logging
  4. Secrets: Plaintext config → secure vault

  5. Testing: Zero tests → comprehensive coverage

  6. Phase 2: Strangle platform dependencies

  7. Hosting: IIS on Windows → containers on managed platform
  8. Database: LocalDB → managed cloud database
  9. Frontend: ASPX + jQuery 1.3.2 → Razor + modern frontend (or SPA)

  10. Observability: None → APM + metrics + tracing

  11. Phase 3: Strangle framework dependencies

  12. Runtime: .NET Framework 3.5/4.0 → .NET 6+/8
  13. Web framework: ASP.NET MVC 2 → ASP.NET Core MVC
  14. ORM: NHibernate 2.1 → Entity Framework Core 6+
  15. Authentication: ASP.NET Membership → ASP.NET Core Identity

NOT Microservices Decomposition (common misconception): - ❌ Strangler Fig does NOT require breaking monolith into microservices - ✅ Strangler Fig works for modernizing monoliths while keeping monolithic architecture - 🎯 Focus: Technology modernization, NOT architectural decomposition

🧩 Component Modernization Strategy

Component: Session State Management

Current Implementation: - Technology: In-process session state (<sessionState mode="InProc" />) - Location: Web.config configuration - Usage: Shopping basket, user preferences, authentication state - Issue: Lost on application restart, prevents horizontal scaling

// Data/Configurations/OrderConfiguration.cs
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.ToTable("Orders");

        builder.HasKey(o => o.Id);
        builder.Property(o => o.Id)
            .HasColumnName("OrderId")
            .ValueGeneratedOnAdd();

        builder.Property(o => o.OrderDate)
            .HasColumnName("OrderDate")
            .IsRequired();

        builder.Property(o => o.OrderState)
            .HasColumnName("OrderState")
            .HasConversion<int>() // Enum → int
            .IsRequired();

        builder.Property(o => o.TotalAmount)
            .HasColumnName("TotalAmount")
            .HasPrecision(18, 2)
            .IsRequired();

        builder.HasOne(o => o.Customer)
            .WithMany()
            .HasForeignKey("CustomerId")
            .IsRequired();

        builder.HasMany(o => o.OrderItems)
            .WithOne()
            .HasForeignKey("OrderId")
            .OnDelete(DeleteBehavior.Cascade);
    }
}

🔒 Security Architecture

Current Security Posture

Authentication: - Forms Authentication (<authentication mode="Forms" />) - ASP.NET Membership with SQL Server provider (SHA1 password hashing - WEAK) - Janrain Social Login (OAuth-style callback for Facebook, Google, Twitter) - Issue: Weak password hashing (SHA1 vulnerable to rainbow tables), no MFA

Authorization: - Role-Based Access Control (basic implementation) - Authorization Attributes on controller actions [Authorize(Roles="Admin")] - Issue: Limited granularity, no claims-based authorization

Data Protection: - Plaintext Secrets in Web.config (CRITICAL VULNERABILITY) - No Encryption at Rest for sensitive data (database not encrypted) - No Column-Level Encryption for sensitive fields (credit cards not stored, but addresses unencrypted) - Issue: Configuration file exposure risk, no defense-in-depth

Network Security: - HTTPS for external communication (PayPal, Janrain) - HTTP for internal communication (assumed - no Load Balancer currently) - Issue: No WAF, no DDoS protection, no rate limiting

Input Validation: - Data Annotations on view models (basic validation) - jQuery Validation client-side (vulnerable jQuery 1.3.2) - No Centralized Validation framework - Issue: Inconsistent validation, no anti-forgery tokens globally

Evidence: security-controls.json, vulnerability-assessment.json

Target Security Architecture

Authentication (Modern & Secure): - ASP.NET Core Identity with bcrypt/Argon2 password hashing - External Identity Provider (Auth0, Azure AD B2C, Okta) for OAuth/OIDC - Multi-Factor Authentication support (TOTP, SMS, email) - Passwordless Options (Magic links, WebAuthn) - Benefits: Strong hashing, MFA, delegated auth management, industry best practices

Authorization (Claims-Based): - Claims-Based Authorization in ASP.NET Core - Policy-Based Authorization for complex rules - JWT Tokens for API authentication (if SPA frontend) - Benefits: Fine-grained control, extensible, standard protocol

Data Protection (Defense-in-Depth): - Secrets Management: Azure Key Vault / AWS Secrets Manager / GCP Secret Manager - Encryption at Rest: Database encryption (TDE or vendor-managed) - Encryption in Transit: TLS 1.2+ for all communication - Column-Level Encryption: For highly sensitive data (if applicable) - Benefits: No plaintext secrets, layered security, compliance-ready

Network Security (Perimeter Protection): - Web Application Firewall (WAF) at edge - DDoS Protection (Cloud provider native) - Rate Limiting at API gateway / load balancer - HTTPS Everywhere with TLS 1.2+ only - Benefits: Attack surface reduction, traffic filtering, availability protection

Input Validation (Comprehensive): - Centralized Validation with Data Annotations + Fluent Validation - Anti-Forgery Tokens on all state-changing operations - Content Security Policy headers to prevent XSS - Parameterized Queries throughout (EF Core default) - Benefits: Injection prevention, XSS mitigation, consistent validation

⚠️ Technical Risks & Mitigations

Risk 1: Data Migration Failure

Risk: Data corruption or loss during database migration from LocalDB to cloud database

Probability: MEDIUM (complex migrations have 10-20% issue rate)
Impact: HIGH (potential data loss, business disruption)
Severity: HIGH

Mitigation Strategies: 1. Pre-Migration Backup: Full backup of LocalDB before migration start 2. Data Validation: Checksum validation (row counts, critical field sums) 3. Test Migration: Perform migration on test environment first 4. Parallel Running: Keep LocalDB as backup during initial cloud DB operation 5. Rollback Plan: Documented rollback procedure with timing estimates 6. Incremental Cutover: Migrate aspnetdb first (lower risk), then Shop.mdf

Validation: Row count matching, foreign key integrity checks, sample data verification

Risk 2: Framework Migration Breaking Changes

Risk: .NET Framework → .NET 6+ migration introduces breaking changes causing functionality loss

Probability: HIGH (significant API changes between Framework and .NET 6+)
Impact: MEDIUM (features broken, may require rework)
Severity: MEDIUM-HIGH

Mitigation Strategies: 1. Comprehensive Testing: 60%+ test coverage before migration (Phase 1) 2. Incremental Migration: Migrate project by project, test after each 3. API Compatibility Analysis: Use .NET Upgrade Assistant to identify breaking changes 4. Compatibility Shims: Use compatibility packages where possible 5. Team Training: Ensure team familiar with .NET 6+ differences before migration

Validation: All automated tests passing, manual regression testing of critical paths

Risk 3: Performance Degradation

Risk: Cloud deployment or framework changes result in performance degradation

Probability: MEDIUM (common in cloud migrations)
Impact: HIGH (user experience, potential revenue loss)
Severity: MEDIUM-HIGH

Mitigation Strategies: 1. Baseline Metrics: Establish current performance baseline before changes (Phase 2 - APM) 2. Load Testing: Performance testing in test environment before production 3. Gradual Rollout: Canary deployment starting with 5-10% traffic 4. Performance Budget: Define acceptable performance thresholds (P95 latency, etc.) 5. Rollback Plan: Automatic rollback if performance SLO breached

Validation: APM monitoring showing performance within baseline ±10%

Risk 4: Scope Creep During Modernization

Risk: Stakeholders request new features during modernization, delaying delivery

Probability: HIGH (very common in long-running projects)
Impact: MEDIUM (timeline extension, cost increase)
Severity: MEDIUM

Mitigation Strategies: 1. Phased Approach: Clear phase boundaries with go/no-go decisions 2. Change Control: Formal change request process for scope additions 3. Backlog Management: New features go to backlog for post-modernization 4. Stakeholder Communication: Regular updates on modernization progress and priorities 5. Definition of Done: Clear acceptance criteria for each phase

Validation: Phase completion without added scope, timeline adherence

📈 Performance & Scalability

Current Performance Characteristics

Performance Profile (from static analysis, NOT runtime measurements): - N+1 Query Risk: HIGH - Lazy loading throughout NHibernate configuration - Caching: NONE active (NHibernate second-level cache not configured) - Synchronous Only: No async/await patterns (not supported in .NET 3.5/4.0) - Session State: In-memory (fast but limits scalability)

Cannot Measure Without Runtime Data: - Request throughput (req/sec) - Response time (p50/p95/p99 latency) - Concurrent user capacity - Database query performance - Memory consumption

Required for Baseline: APM implementation in Phase 2

Evidence: performance-profile.json, query-performance.json

Target Performance Architecture

Async/Await Throughout: - Pattern: Convert synchronous I/O to async (database, HTTP calls, file I/O) - Benefits: Better resource utilization, higher throughput, improved scalability - Implementation: ASP.NET Core controllers with async actions, EF Core async queries

Comprehensive Caching Strategy: - L1: Client-Side Cache: Browser caching for static content (CDN) - L2: Distributed Cache: Redis for application cache (product catalog, categories) - L3: Database Query Cache: EF Core query cache (readonly queries) - L4: Database Result Cache: Database-level result cache if supported - Benefits: Reduced database load, faster response times, lower latency

Query Optimization: - Eager Loading: Use .Include() for related entities when needed (prevent N+1) - Projection: Select only required columns with .Select() - Pagination: Implement paging for list queries (prevent large result sets) - Indexing: Add database indexes based on APM query analysis

Horizontal Scaling: - Auto-Scaling: Scale out based on CPU/memory/request metrics - Stateless Application: All state in distributed cache or database - Load Balancing: Traffic distribution across instances - Benefits: Handle traffic spikes, high availability, cost optimization
